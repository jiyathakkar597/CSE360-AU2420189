# Project Evaluation, Documentation & Generic Graphics

## The core idea: what is actually evaluated?

The project is not evaluated only by how many features or buttons are added.

A major part of the evaluation is **understanding** — especially individual understanding during the presentation.

The instructor may ask questions such as:

* What does this class do?
* Why did you implement it this way?
* What does this particular part of the code do?
* How do the different components work together?

So the important principle is:

**A working project is not enough — you should understand your own implementation.**

## Focus on requirements instead of unnecessary features

Once the required functionality is complete, there is no need to keep adding random features.

Instead, focus on:

* Completing the required functionality
* Understanding the implementation
* Improving documentation
* Making the project easy to demonstrate

Adding more features does not automatically improve the project if the core requirements are not properly understood or documented.

## Documentation

Good documentation should make it easy for someone else to understand the project.

It should clearly explain:

1. What the project does
2. What needs to be done first
3. What happens next
4. How the different components are connected
5. How the project is used

The evaluator should not have to spend a lot of time figuring out how the application works.

### The main goal

**Documentation should reduce the amount of explanation needed during evaluation.**

## Understanding your own code

During the presentation, each member should be prepared to explain their own code.

For example, if the instructor points to a class and asks:

> "What is this class doing?"

The answer should explain its actual purpose rather than simply saying that it is "part of the project."

This means understanding:

* Classes
* Methods
* Important variables
* Graphics components
* How different parts interact

## Generic programming with shapes

One important concept discussed was **generic programming**.

Suppose a program needs to work with different geometric objects such as:

* Lines
* Rectangles
* Circles
* Other shapes

Instead of creating completely separate logic for every type, we can use a common `Shape` abstraction.

The basic idea is:

```text
Shape
 ├── Line
 ├── Rectangle
 ├── Circle
 └── Other shapes
```

This allows common graphics code to work with different kinds of shapes.

## Why generic code is useful

Without generic programming, we might need separate code for every shape.

With a common abstraction, the same general logic can handle different shapes.

For example:

```text
Create a Shape
      ↓
Pass the Shape to the graphics system
      ↓
Draw the Shape
```

This makes the program:

* More reusable
* Easier to extend
* Less repetitive
* More general

## Shape and graphics context

The discussion connected `Shape` objects with the graphics context used for drawing.

The general idea is:

```text
Shape object
     ↓
Graphics / Graphics2D context
     ↓
Rendered shape
```

The graphics context provides the mechanism for actually drawing the shape.

Therefore, instead of writing completely different drawing infrastructure for every geometric object, shapes can be handled through a common interface/abstraction.

## Improving the project

Project improvement should be meaningful rather than simply adding more functionality.

Possible areas for improvement include:

* Cleaner organization
* Better documentation
* Clearer user interaction
* Better use of graphics abstractions
* Demonstrating concepts beyond the minimum requirement

The main goal is to show **understanding and good design**, not just a large number of features.

## Overall takeaway

The lecture connected project evaluation with software design.

A good project should not only **work**, but should also be:

**Understandable → Documented → Well-structured → Explainable**

For graphics programming specifically, using generic abstractions such as `Shape` makes it possible to handle different geometric objects using common drawing logic.
