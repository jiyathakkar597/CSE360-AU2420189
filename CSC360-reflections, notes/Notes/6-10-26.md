## 1. Mathematical Definitions: Sets, Graphs, and Dependence

### 1.1 Importance of Precise Definitions

The lecture emphasized the importance of giving precise, formal definitions rather than relying on vague descriptions.

In mathematics and computer science, a definition must specify exactly what an object is and what conditions it satisfies.

For example, describing something as "good" is subjective because different people may interpret it differently. A mathematical definition should instead use clearly specified conditions.

**Key principle:** If you make a claim about whether something qualifies as a particular object, you should be able to justify your answer using its definition.

### 1.2 What Is a Set?

A set is a well-defined collection of distinct elements.

For example,

\[
A = \{1,2,3,4\}
\]

is a set containing four elements.

The membership of a set must be unambiguous. A description based on an undefined subjective condition, such as "all good students," may not specify a well-defined set.

### 1.3 What Is a Graph?

A graph is a mathematical structure consisting of vertices and edges.

It is commonly represented as

\[
G=(V,E)
\]

where:
- \(V\) is the set of vertices.
- \(E\) is the set of edges connecting vertices.

For an undirected graph, an edge can be represented as an unordered pair of vertices.

For example,

\[
V=\{A,B,C\}
\]

and

\[
E=\{\{A,B\},\{B,C\}\}
\]

describe a graph in which \(A\) is connected to \(B\), and \(B\) is connected to \(C\).

A **directed graph** has edges with a specified direction. Its edges are represented as ordered pairs.

For example,

\[
E=\{(A,B),(B,C)\}
\]

represents directed edges from \(A\) to \(B\) and from \(B\) to \(C\).

### 1.4 Dependence and Independence

The lecture briefly discussed dependence and independence in the context of mathematical problem-solving.

These concepts are important when determining whether conditions or equations impose restrictions on one another.

For example, in linear algebra, a collection of vectors is linearly independent if the only solution to

\[
c_1v_1+c_2v_2+\cdots+c_nv_n=0
\]

is

\[
c_1=c_2=\cdots=c_n=0.
\]

If a nontrivial combination produces the zero vector, the vectors are linearly dependent.

## 2. JavaFX Event Handling

The lecture discussed mouse-driven interactions in a graphical application and asked how JavaFX captures user actions.

### 2.1 Event Handling

An event is an action or occurrence that an application can respond to.

Examples include:
- Clicking the mouse.
- Pressing a button.
- Moving the mouse.
- Pressing a keyboard key.

JavaFX allows developers to register event handlers or listeners that execute when specified events occur.

For example, a mouse click can be handled using:

```java
node.setOnMouseClicked(event -> {
    System.out.println("Mouse clicked");
});
```

Here:
- `node` is the JavaFX component receiving the event.
- `setOnMouseClicked()` registers a handler for mouse-click events.
- `event` contains information about the mouse event.
- The code inside the handler executes when the event occurs.

### 2.2 Separating Event Handling from Other Logic

The instructor asked students to identify where the logic associated with a user interaction was implemented.

When investigating an interactive application, determine:

1. Which component receives the event?
2. Which handler or listener processes it?
3. What logic executes after the event?
4. Which objects are modified?
5. How does the application display the result?

This helps explain how the application works instead of simply describing what happens when the user clicks something.

**Key takeaway:** When presenting an interactive project, explain the event-handling mechanism and the code responsible for the resulting behaviour.

## 3. Project Dependencies and Version Management

The lecture discussed how projects can depend on specific versions of programming tools or libraries.

This is important when several developers work on the same project or when a project must run on different computers.

### 3.1 The Problem with Different Versions

Suppose two developers work on the same project.

One developer has version 3.4 of a dependency installed, while the project requires version 3.5.

If the project uses whichever version happens to be installed locally, the developers may experience different behaviour.

Possible consequences include:
- Compilation errors.
- Missing or changed APIs.
- Different runtime behaviour.
- Difficulty reproducing bugs.
- Problems when integrating code from different developers.

The specific dependency version numbers in this example are illustrative.

### 3.2 Why Specify Dependency Versions?

A project should identify the dependencies and versions it requires.

This helps ensure that the project is built and tested using the intended versions rather than relying on whichever versions happen to be installed.

Dependency management tools can download the required libraries and manage project configuration.

For example, Maven uses a `pom.xml` file to specify project dependencies.

A simplified example is:

```xml
<dependency>
    <groupId>org.example</groupId>
    <artifactId>example-library</artifactId>
    <version>1.0.0</version>
</dependency>
```

The coordinates above are illustrative; they do not identify a specific library from the lecture.

### 3.3 Why Is This Important for Team Projects?

When developers share a project, they should be able to build it without manually guessing which library versions are needed.

Explicit dependency configuration makes the project more reproducible and easier to maintain.

**Key takeaway:** The goal is not necessarily to install identical versions of every tool on every computer. It is to ensure that the project uses the dependencies and versions it requires.

## 4. Java Records Versus Classes

The lecture discussed Java records and asked what additional code might be required if a record were replaced with a regular class.

### 4.1 What Is a Record?

A Java record is a concise way to declare a class whose primary purpose is to represent data.

For example:

```java
public record Point(double x, double y) {
}
```

This declares a record named `Point` with two components:
- `x`
- `y`

Java automatically provides several features, including:
- A canonical constructor.
- Accessor methods.
- `equals()`.
- `hashCode()`.
- `toString()`.

This reduces the amount of repetitive code needed for a simple data carrier.

### 4.2 Replacing a Record with a Class

The same basic data structure can be represented using a regular class.

For example:

```java
public class Point {
    private final double x;
    private final double y;

    public Point(double x, double y) {
        this.x = x;
        this.y = y;
    }

    public double x() {
        return x;
    }

    public double y() {
        return y;
    }
}
```

This class provides the fields, constructor, and accessors explicitly.

However, it does not automatically provide the same generated `equals()`, `hashCode()`, and `toString()` implementations as the record. Those methods would need to be implemented if equivalent behaviour were required.

### 4.3 Why Use a Record?

Records are useful when:
- The main purpose of a type is to hold data.
- The data components are clearly defined.
- Boilerplate code should be minimized.
- Value-based equality is appropriate.

Regular classes are more suitable when a type requires behaviour or design flexibility that does not fit the restrictions of records.

**Key takeaway:** A record reduces boilerplate for data-oriented classes, while a regular class gives the developer more flexibility over the implementation.

## 5. Tree Visualization and Layout

A major part of the lecture focused on a project that draws a tree.

The instructor emphasized that a presentation should explain the actual technical challenges of drawing the tree rather than discussing unrelated details or assuming that the audience already understands the implementation.

### 5.1 The Core Challenge

A tree visualization must convert a tree's logical structure into positions on a two-dimensional canvas.

Each node must be assigned a position, and the connections between nodes must be drawn appropriately.

A simplified tree might look like this:

```text
          A
         / \
        B   C
       / \
      D   E
```

The program must determine where to place each node and how to draw the connecting edges.

### 5.2 Why Fixed Positions Can Be a Problem

Suppose a program assigns every node a hard-coded position.

The tree might look correct for one particular canvas size, but the layout could become unsuitable if:
- The window becomes larger.
- The window becomes smaller.
- The tree contains more nodes.
- The tree becomes deeper.
- The tree has an uneven structure.

For example, a tree designed for a wide canvas might extend beyond the boundaries of a smaller canvas.

Therefore, the layout should be calculated from the tree structure and available drawing space rather than relying unnecessarily on fixed coordinates.

### 5.3 Information Needed to Calculate Node Positions

The lecture discussed determining node dimensions and positions from the structure of the tree.

Relevant information can include:
- The number of nodes.
- The tree's height.
- The number of nodes at each level.
- The available canvas width and height.
- The spacing required between nodes.
- The positions of parent and child nodes.

The precise layout algorithm used by the project was not fully captured in the transcript.

### 5.4 A Simple Example of Level-Based Positioning

For a basic binary tree, nodes can be assigned vertical positions based on their depth.

For example,

\[
y_d=y_0+d\cdot s_y
\]

where:
- \(y_0\) is the vertical position of the root.
- \(d\) is the node's depth.
- \(s_y\) is the vertical spacing between levels.

A node at depth 0 is the root. Its children are at depth 1, and their children are at depth 2.

Horizontal positions require a separate layout rule that accounts for the arrangement of nodes at each level.

This equation is an illustrative approach, not the specific algorithm identified in the transcript.

### 5.5 Separating Tree Data from Drawing Coordinates

The lecture questioned why coordinate information was stored in particular objects and whether it should be stored directly in the tree nodes.

This raises an important design consideration: **where should layout information belong?**

A tree node may contain structural information such as:
- Its value.
- Its left child.
- Its right child.

A separate layout representation may contain:
- Its x-coordinate.
- Its y-coordinate.
- Its calculated drawing dimensions.

Keeping these responsibilities separate can be useful when the same tree structure needs to be displayed in different layouts.

However, the appropriate design depends on the project's requirements. Storing coordinates in the node itself can also be reasonable when the node is explicitly designed to represent a positioned visual element.

The important point is to understand and justify the design rather than duplicate information without a clear reason.

### 5.6 What Should Be Explained in a Tree-Drawing Project?

A strong technical explanation should cover:
1. How the tree is represented in code.
2. How the program traverses or processes the tree.
3. How node positions are calculated.
4. How the canvas dimensions affect the layout.
5. How edges are drawn between parent and child nodes.
6. How the implementation handles trees of different sizes.
7. What the most challenging part of the implementation was.

**Key takeaway:** Explaining how the tree is actually laid out and drawn is more important than merely showing that the final image looks correct.

## 6. Software Design and Maintainability

The instructor emphasized the importance of making design decisions carefully, particularly when deciding where information should be stored.

### 6.1 Avoid Unnecessary Duplication

If the same information is stored in multiple places, the program may need additional logic to keep those copies consistent.

For example, if node coordinates are stored both in a tree node and in a separate layout object, the developer must decide which representation is authoritative.

Without a clear reason for the duplication, changes can become harder to manage.

### 6.2 Separate Responsibilities

A program is easier to understand when each component has a clear purpose.

For a tree visualization, responsibilities might include:
- Representing the tree structure.
- Calculating the layout.
- Drawing nodes and edges.
- Responding to user interactions.

These responsibilities can be placed in separate components when doing so improves clarity and maintainability.

### 6.3 Justify Design Decisions

When selecting a data structure or deciding where to store a property, ask:
- What information does this object represent?
- Who needs access to the information?
- Can the information be calculated when required?
- Would storing it in multiple places create inconsistency?
- How would the design handle future changes?

**Key takeaway:** Code should not only work for the current example; its structure should also make sense and support reasonable changes.

## 7. Technical Presentations and Genuine Understanding

The instructor repeatedly emphasized that a presentation should make sense to someone who has never seen the project before.

### 7.1 Explain the Project from the Audience's Perspective

Do not assume that the audience already knows:
- What the application does.
- How its interface works.
- How the underlying data is represented.
- Which part of the code is responsible for a feature.

Introduce the project clearly before discussing implementation details.

### 7.2 Focus on the Main Technical Challenge

If a project is about drawing a tree, the presentation should explain the challenges of tree representation, layout calculation, and drawing.

Spending too much time discussing secondary features can distract from the main learning objective.

### 7.3 Understand Code That Was Reused

The instructor challenged students to move beyond code that already works and understand why it works.

When using an existing example or adapting code from another source:
- Trace how the code executes.
- Identify the important methods.
- Understand the data structures involved.
- Investigate the difficult implementation decisions.
- Be prepared to explain the approach and its limitations.

### 7.4 Tell a Logical Story

A technical presentation should follow a clear sequence:

1. Introduce the problem.
2. Explain why it matters.
3. Describe the proposed approach.
4. Explain the core implementation.
5. Discuss the main technical challenge.
6. Demonstrate the result.
7. Explain the limitations or possible improvements.

**Key takeaway:** A presentation should demonstrate learning and understanding, not just show a working application.
